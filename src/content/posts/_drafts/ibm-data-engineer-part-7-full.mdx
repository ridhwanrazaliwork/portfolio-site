## Chapter 1 — Machine learning with Apache Spark

### What machine learning is

**ELI5:** instead of writing rules for every case, you show the computer lots of examples and it learns the rules itself.

Traditional programming:

```text
rules + data → answers
```

Machine learning:

```text
data + answers → rules (model)
```

- **Model** — the learned pattern: a mathematical function that maps inputs to predictions.
- **Features** — the input variables used to predict.
- **Label / target** — the thing you want to predict in supervised learning.
- **Training** — learning the model from data.
- **Inference / scoring** — using a trained model to make predictions.

ML is good for prediction, classification, recommendation, anomaly detection, clustering, and generation. It is a poor fit when there is no data, when rules are strictly deterministic, or when explainability is legally required and cannot be provided.

### The data engineer's role in ML

**ELI5:** data engineers build the kitchen and stock the fridge; data scientists cook the model.

Data engineers make ML possible by providing:

- Access to clean, reliable data.
- Pipelines that refresh training data.
- Feature stores or feature tables so features stay consistent.
- Scalable storage and compute.
- Data quality checks and schema enforcement.
- Governance, lineage, and security.

Bad data engineering shows up as stale features, training/serving skew, missing values, duplicate rows, and models that cannot be reproduced. A great model on bad data is still a bad model.

### The ML lifecycle

**ELI5:** a model is like a plant — prepare the soil, plant it, water it, watch it grow, and keep pruning.

| Stage | Question |
| :--- | :--- |
| **1. Problem framing** | What decision will the model support? What is success? |
| **2. Data collection** | Is the data relevant and representative? |
| **3. Data preparation** | Clean, join, handle missing values, engineer features |
| **4. Splitting** | Train, validation, and test sets |
| **5. Training** | Fit the model on the training set |
| **6. Evaluation** | Measure performance on held-out data |
| **7. Tuning** | Adjust hyperparameters, features, or algorithm |
| **8. Deployment** | Serve as batch, real-time API, or embedded model |
| **9. Monitoring** | Watch for drift, errors, and performance decay |
| **10. Retraining** | Refresh with new data and repeat |

Three dataset roles:

| Set | Purpose |
| :--- | :--- |
| **Training** | Examples the model learns from |
| **Validation** | Tune and compare models |
| **Test** | Held out until the end; estimates real-world performance |

**Data leakage** is when information from the test set sneaks into training. It produces fake-good results. **Reproducibility** means the same data, code, and parameters produce the same model.

### Supervised versus unsupervised learning

**ELI5:** supervised learning is studying with an answer key; unsupervised learning is sorting a pile of stuff without labels.

| | Supervised | Unsupervised |
| :--- | :--- | :--- |
| **Data** | Inputs plus labels | Inputs only |
| **Goal** | Predict the label | Find structure |
| **Tasks** | Regression, classification | Clustering, dimensionality reduction, association |
| **Examples** | Price prediction, spam detection | Customer segmentation, anomaly detection |
| **Evaluation** | Compare predictions with known answers | Internal metrics such as silhouette |

Other paradigms: **semi-supervised** (small labeled set plus large unlabeled set), **self-supervised** (labels generated from the data, common in LLMs), and **reinforcement learning** (an agent learns from rewards and penalties).

The problem type determines the algorithm, metric, and data preparation.

### Regression

**ELI5:** regression draws the best line through scattered dots so you can predict a number for a new dot.

**Regression** predicts a continuous numeric value: house price, temperature, sales, noise level, or delivery time.

**Linear regression** fits a line or hyperplane:

```text
y = b0 + b1x1 + b2x2 + ...
```

- **Slope** — how much `y` changes when `x` increases by one.
- **Intercept** — predicted `y` when all inputs are zero.
- **Simple linear regression** — one feature.
- **Multiple linear regression** — many features.
- **Ordinary Least Squares (OLS)** — chooses coefficients that minimize squared errors.

Assumptions, roughly: a linear relationship, independent errors, constant variance, and roughly normal residuals.

**Regularization** penalizes large coefficients to prevent overfitting:

| Method | Effect |
| :--- | :--- |
| **Ridge (L2)** | Shrinks coefficients |
| **Lasso (L1)** | Can push coefficients to zero, selecting features |
| **Elastic net** | Combines L1 and L2 |

**Polynomial regression** fits curves by adding squared or cubed features.

- **Overfitting** — memorizes training noise; great on train, poor on test.
- **Underfitting** — too simple; poor on both.

SparkML regressors include `LinearRegression`, `GeneralizedLinearRegression`, `DecisionTreeRegressor`, `RandomForestRegressor`, `GBTRegressor`, and `FactorizationMachines`.

```python
from pyspark.ml.regression import LinearRegression

lr = LinearRegression(featuresCol="features", labelCol="label")
model = lr.fit(train)
preds = model.transform(test)
print(model.coefficients, model.intercept)
```

### Classification

**ELI5:** classification sorts things into buckets — spam or not spam, sick or healthy.

**Classification** predicts a category:

| Type | Meaning |
| :--- | :--- |
| **Binary** | Two classes, such as fraud or not fraud |
| **Multiclass** | More than two classes, such as digit 0–9 |
| **Multilabel** | Multiple labels can be true at once |

Common algorithms:

| Algorithm | Notes |
| :--- | :--- |
| **Logistic regression** | A classification algorithm despite the name; outputs a probability |
| **Decision tree** | Interpretable, prone to overfitting |
| **Random forest** | Many trees voting; more robust |
| **Gradient-boosted trees** | Sequential trees correcting errors; strong performance |
| **Naive Bayes** | Fast probabilistic baseline, good for text |
| **Linear SVC** | Finds a separating boundary |
| **Multilayer perceptron** | Neural network for complex patterns |

**Class imbalance** is a common trap: accuracy becomes misleading when one class is rare. Use precision, recall, F1, resampling, or class weights. Tune the probability threshold to the business cost of false positives versus false negatives.

### Evaluation metrics

**ELI5:** a test score for your model — but you need the right test, or you will celebrate the wrong thing.

Regression:

| Metric | Meaning |
| :--- | :--- |
| **MAE** | Average absolute error; same units as the target |
| **MSE** | Average squared error; penalizes large errors |
| **RMSE** | Square root of MSE; same units as the target |
| **R²** | Proportion of variance explained; 1 is perfect, 0 is no better than the mean |
| **MAPE** | Mean absolute percentage error; breaks when actual values are zero |

Classification:

| Metric | Question |
| :--- | :--- |
| **Confusion matrix** | Counts of true positives, true negatives, false positives, false negatives |
| **Accuracy** | Overall correct rate; misleading with imbalance |
| **Precision** | Of the ones flagged, how many were right? |
| **Recall** | Of the real positives, how many were caught? |
| **F1** | Harmonic mean of precision and recall |
| **ROC / AUC** | Tradeoff across thresholds; 0.5 is random, 1.0 is perfect |
| **PR / AUC-PR** | Better than ROC when positives are rare |
| **Log loss** | Penalizes confident wrong probabilities |

Clustering:

| Metric | Meaning |
| :--- | :--- |
| **Silhouette** | Similarity to own cluster versus others; −1 to 1, higher is better |
| **WSSSE / inertia** | Compactness; lower is better, but always decreases with more clusters |
| **Davies–Bouldin** | Alternative internal metric |

Best practices: evaluate on held-out data, use cross-validation for small datasets, report several metrics, compare against a baseline, and watch for leakage and overfitting to the test set.

### Clustering

**ELI5:** clustering groups similar things without being told what the groups are — like sorting a mixed pile of socks by color and size.

- **K-Means** — partitions into `k` clusters by minimizing distance to cluster centers.
- Choose `k` in advance.
- Iterates: assign points, recompute centers.
- Sensitive to initialization and scale.
- Use **k-means++** initialization.

Choosing `k`:

- **Elbow method** — plot WSSSE against `k` and look for the bend.
- **Silhouette** — choose the `k` with the best separation.
- Business interpretability matters too.

Other approaches: hierarchical clustering, DBSCAN, Gaussian mixture, and bisecting K-Means. Always scale features before distance-based clustering.

### SparkML

**ELI5:** SparkML is a box of model parts that snap together into a pipeline.

SparkML provides:

- Regression, classification, clustering, recommendation, and feature transformers.
- A **Pipeline** abstraction that chains transformers and estimators.
- **CrossValidator** and **TrainValidationSplit** for tuning.
- **PipelineModel** persistence for deployment.

Feature extraction:

| Tool | Use |
| :--- | :--- |
| `Tokenizer`, `RegexTokenizer` | Split text into words |
| `StopWordsRemover` | Drop common words |
| `NGram` | Word pairs or triples |
| `HashingTF`, `CountVectorizer` | Text to numeric vectors |
| `IDF` | Downweight common words |
| `Word2Vec` | Word embeddings |
| `VectorAssembler` | Combine columns into one `features` vector |

Feature transformation:

| Tool | Use |
| :--- | :--- |
| `StringIndexer` | Categorical strings to numeric indices |
| `OneHotEncoder` | Indices to binary vectors |
| `IndexToString` | Predictions back to labels |
| `StandardScaler` | Mean 0, unit variance |
| `MinMaxScaler` | Scale to a range |
| `Normalizer` | Unit norm per row |
| `Binarizer` | Threshold to 0 or 1 |
| `Bucketizer` | Continuous values to bins |
| `PCA` | Dimensionality reduction |
| `PolynomialExpansion` | Interaction and power terms |

Most SparkML models require a single `features` vector, so `VectorAssembler` is almost always in the pipeline.

Fit transformers on **training data only**, then apply them to validation and test data. A `Pipeline` handles this automatically.

### ML pipelines and persistence

**ELI5:** a pipeline is an assembly line — each station transforms the data, and the last station trains the model.

A **Pipeline** is an ordered list of stages: transformers and estimators. `pipeline.fit(train)` runs all stages and returns a **PipelineModel**. `PipelineModel.transform(new_data)` applies the same transformations and predictions.

Why pipelines matter:

- Prevent **training/serving skew**.
- Keep preprocessing reproducible.
- Make cross-validation and tuning clean.
- Give you one object to save and deploy.

```python
from pyspark.ml import Pipeline
from pyspark.ml.feature import VectorAssembler, StandardScaler
from pyspark.ml.regression import LinearRegression

assembler = VectorAssembler(
    inputCols=["feature1", "feature2"], outputCol="features"
)
scaler = StandardScaler(
    inputCol="features", outputCol="scaledFeatures"
)
lr = LinearRegression(
    featuresCol="scaledFeatures", labelCol="label"
)

pipeline = Pipeline(stages=[assembler, scaler, lr])
model = pipeline.fit(train)
predictions = model.transform(test)
```

Hyperparameter tuning:

```python
from pyspark.ml.tuning import CrossValidator, ParamGridBuilder

paramGrid = (ParamGridBuilder()
             .addGrid(lr.regParam, [0.01, 0.1, 1.0])
             .addGrid(lr.elasticNetParam, [0.0, 0.5, 1.0])
             .build())

cv = CrossValidator(
    estimator=pipeline,
    estimatorParamMaps=paramGrid,
    evaluator=evaluator,
    numFolds=3,
)

cv_model = cv.fit(train)
best = cv_model.bestModel
```

**Hyperparameters** are settings you choose before training, such as `k`, regularization, or tree depth. **Parameters** are learned from data, such as coefficients and splits.

Persistence:

```python
# Save
model.write().overwrite().save("models/airfoil")

# Load
from pyspark.ml import PipelineModel
loaded = PipelineModel.load("models/airfoil")
loaded.transform(new_data).show()
```

Save the **PipelineModel**, not just the estimator, so preprocessing travels with the model. Pin the Spark and library versions; a model saved with one version may not load in another. For production, a model registry such as MLflow adds versioning, metrics, and artifacts.

### SparkSQL, ETL, and structured streaming

**ELI5:** SparkSQL lets you query DataFrames with SQL; structured streaming lets the same code process an endless table.

SparkSQL turns a DataFrame into a temporary view:

```python
df.createOrReplaceTempView("sales")
spark.sql("""
    SELECT region, SUM(amount) AS total
    FROM sales
    GROUP BY region
    ORDER BY total DESC
""").show()
```

ETL with DataFrames follows the same extract-transform-load pattern as Part 5, but distributed:

```python
raw = spark.read.csv("raw.csv", header=True, inferSchema=True)
clean = raw.dropna().dropDuplicates(["id"])
enriched = clean.join(ref, on="id", how="left")
enriched.write.mode("overwrite").parquet("output/")
```

**Structured Streaming** treats a stream as an unbounded table:

```python
stream = (spark.readStream
          .format("kafka")
          .option("kafka.bootstrap.servers", "host:9092")
          .option("subscribe", "events")
          .load())

query = (stream.writeStream
         .outputMode("append")
         .format("console")
         .option("checkpointLocation", "/tmp/checkpoint")
         .start())

query.awaitTermination()
```

Output modes:

| Mode | Meaning |
| :--- | :--- |
| **Append** | Only new rows |
| **Update** | Changed rows only |
| **Complete** | Full result table, for aggregations |

Checkpointing saves progress so the stream can recover. Watermarks bound late data for event-time aggregations. Exactly-once processing depends on checkpointing plus replayable sources and sinks.

### GraphFrames

**ELI5:** GraphFrames treats data as nodes and edges so you can ask relationship questions.

GraphFrames adds graph processing to Spark:

- **Vertices** — nodes with properties.
- **Edges** — relationships with properties.
- **Motif finding** — pattern matching over paths.
- **PageRank**, connected components, triangle counting, shortest paths.

It is useful for social networks, fraud rings, recommendations, and dependency graphs. For tabular analytics, DataFrames are still the better tool.

### Hands-on lab: airfoil noise prediction

**Scenario:** you are a data engineer at an aeronautics consulting company. Clean the NASA airfoil noise dataset, build an ML pipeline that predicts sound level, evaluate it, and persist the model.

This was the Spark ML final project. It has four parts: ETL, pipeline, evaluation, and persistence.

#### Part 1 — ETL

```python
from pyspark.sql import SparkSession

spark = SparkSession.builder \
    .appName("AirfoilNoisePrediction") \
    .getOrCreate()

df = spark.read.csv(
    "NASA_airfoil_noise_raw.csv",
    header=True,
    inferSchema=True,
)

rowcount1 = df.count()

df = df.dropDuplicates()
rowcount2 = df.count()

df = df.na.drop()
rowcount3 = df.count()

df = df.withColumnRenamed(
    "SoundLevel", "SoundLevelDecibels"
)

df.write.parquet("NASA_airfoil_noise_cleaned.parquet")
```

The checks are deliberate: record the row count before cleaning, after removing duplicates, and after dropping nulls. That is how you prove what the cleaning actually did.

#### Part 2 — Build the pipeline

```python
from pyspark.ml import Pipeline
from pyspark.ml.feature import VectorAssembler, StandardScaler
from pyspark.ml.regression import LinearRegression

df = spark.read.parquet("NASA_airfoil_noise_cleaned.parquet")

assembler = VectorAssembler(
    inputCols=[c for c in df.columns if c != "SoundLevelDecibels"],
    outputCol="features",
)

scaler = StandardScaler(
    inputCol="features",
    outputCol="scaledFeatures",
)

lr = LinearRegression(
    featuresCol="scaledFeatures",
    labelCol="SoundLevelDecibels",
)

pipeline = Pipeline(stages=[assembler, scaler, lr])

training_data, testing_data = df.randomSplit(
    [0.7, 0.3], seed=42
)

pipeline_model = pipeline.fit(training_data)
```

The seed matters for reproducibility. The lab fixes it at `42` so everyone gets the same split and comparable results.

#### Part 3 — Evaluate

```python
from pyspark.ml.evaluation import RegressionEvaluator

predictions = pipeline_model.transform(testing_data)

evaluator = RegressionEvaluator(
    labelCol="SoundLevelDecibels",
    predictionCol="prediction",
    metricName="mse",
)
mse = evaluator.evaluate(predictions)

evaluator = RegressionEvaluator(
    labelCol="SoundLevelDecibels",
    predictionCol="prediction",
    metricName="mae",
)
mae = evaluator.evaluate(predictions)

evaluator = RegressionEvaluator(
    labelCol="SoundLevelDecibels",
    predictionCol="prediction",
    metricName="r2",
)
r2 = evaluator.evaluate(predictions)
```

Report all three. MSE penalizes large errors, MAE is easier to interpret, and R² tells you how much variance the model explains relative to the mean.

#### Part 4 — Persist and reload

```python
pipeline_model.write().save("Final_Project")

from pyspark.ml import PipelineModel

loaded_model = PipelineModel.load("Final_Project")

predictions = loaded_model.transform(testing_data)
predictions.select(
    "SoundLevelDecibels", "prediction"
).show(5)
```

The loaded model should produce the same predictions as the original. That is the persistence test.

> **Gotcha:** `VectorAssembler` must receive numeric columns. If a categorical string slips in, the pipeline fails at fit time.

> **Gotcha:** scaling before the train/test split leaks test information into training. Put the scaler inside the pipeline so it is fit on training data only.

> **Gotcha:** a saved model is tied to its feature schema and Spark version. Keep the pipeline and the version pinned.

### One-page recap

**ELI5:** the whole chapter in one breath.

- ML learns rules from examples rather than being programmed with every rule.
- Data engineers provide clean, reliable, reproducible data and pipelines.
- The lifecycle runs from problem framing through monitoring and retraining.
- Supervised learning uses labels; unsupervised learning finds structure.
- Regression predicts numbers; classification predicts categories; clustering groups similar rows.
- Evaluate with the metric that matches the business cost.
- SparkML chains transformers and estimators into a pipeline.
- Persist the whole pipeline so preprocessing travels with the model.
- Structured streaming applies the same DataFrame model to unbounded data.
- GraphFrames handles relationship-heavy questions.

## Chapter 2 — Generative AI for data engineers

### What generative AI is

**ELI5:** a GenAI model has read an enormous library and learned to predict what comes next — so it can write a plausible paragraph, query, or program.

| Term | Meaning |
| :--- | :--- |
| **Generative AI** | Models that produce new content: text, code, images, audio, video |
| **LLM** | A large language model trained to predict the next token |
| **Token** | A chunk of text; models read and bill by tokens |
| **Context window** | How much text the model can consider at once |
| **Parameters** | Learned weights; larger models are usually more capable but slower and costlier |
| **Temperature** | Randomness control: low is focused, high is varied |
| **Prompt** | The instruction and context you provide |
| **Hallucination** | Confident, fluent, wrong output |
| **Knowledge cutoff** | The model does not know recent events unless given context |
| **Multimodal** | Models that also handle images or audio |

GenAI is useful precisely because it is flexible. That flexibility is also the risk: it can produce a very convincing wrong answer.

### Prompting basics

**ELI5:** a good prompt is a good brief — role, context, task, constraints, and the format you want.

A strong prompt includes:

1. **Role** — "You are a senior data engineer."
2. **Context** — schema, business rules, data types, constraints.
3. **Task** — exactly what to produce.
4. **Constraints** — dialect, version, style, safety rules.
5. **Output format** — SQL only, JSON, table, step-by-step.
6. **Examples** — one or two input/output pairs.
7. **Validation request** — "list assumptions and edge cases."

Example — schema design:

> You are a data engineer. Design a PostgreSQL schema for a ride-sharing app. Requirements: riders, drivers, trips, payments, ratings. Include primary keys, foreign keys, indexes, and a star schema for analytics. Return DDL plus a short explanation of grain and tradeoffs. List any assumptions.

Example — SQL:

> Given this schema: `orders(order_id, customer_id, order_date, total)`, `customers(customer_id, name, region)`. Write a query for monthly revenue by region for 2024. Use only these columns. Return SQL only, then explain the join.

Good habits: iterate, ask for assumptions, ask for tests, break large tasks into steps, provide the schema, and set the audience. Asking for reasoning can help, but do not treat the stated reasoning as proof of correctness.

### Prompting, RAG, fine-tuning, and agents

**ELI5:** RAG lets the model open the right book before answering; fine-tuning teaches it a new habit; an agent lets it use tools.

| Approach | What it does | Best for | Limits |
| :--- | :--- | :--- | :--- |
| **Prompting** | Put instructions and context in the prompt | Quick tasks, drafting | Context limits; no memory |
| **RAG** | Retrieve relevant documents, then answer with them | Company docs, catalogs, policies | Retrieval quality; chunking |
| **Fine-tuning** | Further train on domain examples | Style, format, domain behavior | Cost, data needs, staleness |
| **Agents** | Model plans and calls tools or APIs | Multi-step automation | Error propagation, safety |

**Embeddings** are numeric vectors representing meaning. A **vector database** stores them for similarity search.

RAG flow:

```text
documents
   │
   ▼
chunking
   │
   ▼
embedding model
   │
   ▼
vector database
   │
   ▼ (top-k)
retrieved chunks
   │
   ▼
prompt with context
   │
   ▼
answer with citations
```

**Grounding** ties answers to provided sources. **Citations** force the model to point at the passage. **Guardrails** validate input and output, restrict tools, and enforce permissions.

RAG is not a cure. Bad retrieval or conflicting documents still produce bad answers.

### How data engineers use generative AI

**ELI5:** GenAI is an intern that types fast — great for drafts, dangerous if unsupervised.

| Task | GenAI help | Human must |
| :--- | :--- | :--- |
| **SQL writing** | Draft queries, joins, window functions | Validate schema, results, performance |
| **SQL explanation** | Explain legacy or complex queries | Confirm business logic |
| **Code generation** | PySpark, pandas, Airflow, dbt, tests | Review, run, test |
| **Documentation** | Docstrings, READMEs, data dictionaries | Verify accuracy |
| **Schema design** | DDL, ERDs, normalization suggestions | Check keys, grain, constraints |
| **Data quality** | Generate validation rules and tests | Tune thresholds and edge cases |
| **Synthetic data** | Create realistic test datasets | Check privacy and statistical validity |
| **Anonymization** | Suggest masking or pseudonymization | Legal review, re-identification testing |
| **Infrastructure** | Terraform, Docker, Kubernetes manifests | Security, secrets, cost review |
| **Pipeline generation** | ETL/ELT code and orchestration DAGs | Test end-to-end, monitor |
| **Database administration** | Backup, monitoring, tuning advice | Execute carefully, verify backups |
| **Analysis** | EDA code, chart suggestions, summaries | Check statistics and causality |
| **Metadata** | Descriptions, tags, lineage summaries | Confirm against the catalog |
| **Migration** | Translate SQL dialects, plan upgrades | Test compatibility |

Best fit: repetitive drafting, boilerplate, explanation, and first drafts.

Worst fit: irreversible actions, security-critical configuration, legal or compliance decisions, and anything without a test.

### Architecture, planning, and schema design

**ELI5:** use the assistant to sketch the building, then have an architect check the blueprints.

GenAI can draft:

- Requirements to design options.
- Architecture reviews and risk lists.
- Capacity estimates.
- Technology comparisons.
- Entity and relationship proposals.
- Migration plans.
- Architecture decision records.

Always validate against real constraints, cost calculators, and security review.

For schema design, ask for DDL, ERDs, star or snowflake models, indexes, partitioning, naming conventions, and documentation. Then verify:

- Keys: primary, foreign, unique, composite.
- Grain: what one fact row means.
- Data types: exact decimals for money, dates for dates.
- Nullability and defaults.
- Referential integrity and cascade behavior.
- Normalization versus denormalization.
- SQL dialect.
- Performance: indexes, partitions, query patterns.

The risk is plausible-looking DDL that violates a business rule or uses the wrong dialect.

Prompt pattern:

> Given these requirements and access patterns, produce a normalized OLTP schema and a star schema for analytics. Use PostgreSQL syntax. Include keys, constraints, indexes, and a data dictionary. Call out assumptions and any tradeoffs.

### Synthetic data and anonymization

**ELI5:** GenAI can invent realistic practice data — useful for testing, risky if it leaks real patterns.

Synthetic data is artificially generated data that mimics real data. Augmentation expands or balances a dataset with edge cases, minority classes, or rare events.

Uses: test pipelines without production data, fill gaps, balance classes, create demo datasets, and share data with privacy caveats.

Quality checks:

- Schema and type validity.
- Distribution similarity: means, ranges, correlations.
- Referential integrity.
- Business-rule validity.
- No real PII leakage.

Risks: synthetic data can inherit bias, memorize rare real records, miss messy edge cases, and distort production model performance if used carelessly.

Anonymization removes or scrambles the "who":

| Technique | Meaning |
| :--- | :--- |
| **Masking** | Replace characters, such as `****-1234` |
| **Pseudonymization** | Replace identifiers with reversible tokens |
| **Generalization** | Age to age band; city to region |
| **Suppression** | Remove rare or high-risk records |
| **Synthetic data** | Generate replacements |
| **k-anonymity** | Each record is indistinguishable from at least `k−1` others |
| **l-diversity** | Sensitive values are diverse within groups |
| **Differential privacy** | Add calibrated noise to aggregate outputs |

GenAI-specific risks: models may memorize training data, synthetic data may preserve identifying patterns, and prompts themselves can leak sensitive data to a provider.

Best practices: never paste raw PII into public models, use enterprise or private deployments with no-training guarantees, anonymize before prompting, test re-identification risk, and get legal or privacy review.

### Infrastructure and pipelines

**ELI5:** the assistant can draft the plumbing, but a human must check for leaks and locked doors.

Infrastructure drafting:

- Terraform, CloudFormation, or ARM templates.
- Dockerfiles and Compose files.
- Kubernetes manifests.
- Cloud CLI commands.
- Ansible playbooks.
- CI/CD YAML.

Verify secrets, least privilege, network exposure, encryption, cost, state management, idempotency, and rollback. Treat generated infrastructure as a draft pull request, not a deployment.

For ETL, GenAI can draft extraction code, transformations, orchestration DAGs, retries, tests, data-quality checks, and documentation.

Verify:

- Idempotency: reruns do not duplicate.
- Schema handling and evolution.
- Null and edge-case behavior.
- Performance: shuffles, partitioning, skew.
- Security: credentials and PII.
- Orchestration dependencies and retries.

The risk is code that works on a toy sample and fails at scale.

### Repository maintenance and NL2SQL

**ELI5:** the assistant can suggest chores and write scripts — but never let it run destructive commands unchecked.

GenAI can help with backup and restore scripts, monitoring queries, index and statistics recommendations, partition maintenance, user provisioning, health checks, upgrade checklists, and incident summaries.

Verify that backups restore, permissions follow least privilege, destructive commands have guards, maintenance windows are respected, and syntax matches the database.

Never paste production credentials or run generated `DROP`, `DELETE`, or `TRUNCATE` without review.

**NL2SQL** turns a natural-language question into SQL. To improve accuracy:

- Provide the full schema: tables, columns, types, keys.
- Provide non-sensitive sample rows.
- State the dialect and version.
- Define business terms such as "active customer."
- Ask for read-only queries.
- Ask for assumptions and edge cases.

Validate that columns and tables exist, join keys are correct, filters match the business definition, the aggregation grain is right, results make sense, and performance is acceptable.

Risks: hallucinated columns, wrong joins, silent fan-out or double counting, destructive statements, and SQL injection if generated SQL embeds user input.

Use read-only credentials, limit rows, and review before execution.

### Analysis, lakehouse, risks, and responsible AI

**ELI5:** the assistant can suggest what to look at and write the code — but it can also invent patterns that are not there.

GenAI can help with EDA code, visualization suggestions, hypothesis generation, stakeholder summaries, feature ideas, and model interpretation.

Verify statistical significance, effect size, correlation versus causation, sample bias, missing data, multiple-comparison risk, and reproducibility. The model is a brainstorming partner, not a statistician of record.

In a lakehouse, GenAI can generate SQL, summarize metadata and lineage, draft documentation, suggest partitioning, and assist with pipeline code. It does not replace the storage engine, catalog, data quality, or good table design. Governance still applies.

Risks to plan for:

- Accuracy and hallucination.
- Stale knowledge.
- Bias.
- Privacy.
- Security and prompt injection.
- IP and copyright.
- Non-determinism.
- Cost and latency.
- Over-reliance and skill atrophy.
- Accountability.
- Compliance.
- Vendor lock-in.

Responsible GenAI principles:

| Principle | Practice |
| :--- | :--- |
| **Fairness** | Test for bias across groups |
| **Transparency** | Document models, data, and limitations |
| **Explainability** | Be able to justify outputs |
| **Privacy** | Minimize data and protect PII |
| **Security** | Protect models, prompts, and outputs |
| **Accountability** | Name owners and review processes |
| **Human oversight** | Humans approve high-impact actions |
| **Safety and robustness** | Test adversarial and edge cases |

Governance practices: a model inventory, risk assessment, data provenance and consent, prompt and output logging, red-teaming, model cards, and incident response.

### A practical validation workflow

**ELI5:** treat every AI output like a junior colleague's draft — read it, test it, and sign off before it ships.

```text
1. Define the task and constraints
2. Provide the schema and context
3. Ask for assumptions
4. Generate a draft
5. Check syntax and references
6. Run on a small sample
7. Validate results against known answers
8. Review security, privacy, and cost
9. Add tests
10. Human sign-off
```

For high-stakes or irreversible actions, human approval is mandatory.

### Try it: a schema and NL2SQL exercise

There are no lab artifacts for the GenAI course, so here is a small practice exercise instead of a lab walkthrough.

**Exercise 1 — schema draft.** Give a model this prompt:

> You are a data engineer. Design a PostgreSQL schema for a small library: books, authors, members, loans, and fines. Include primary keys, foreign keys, indexes, and a star schema for monthly borrowing analytics. State the grain of each fact and list assumptions.

Then check every key, type, nullability rule, and relationship by hand. Compare the OLTP schema with the star schema and decide whether the grain is clear.

**Exercise 2 — NL2SQL validation.** Give a model a real schema and ask for a query that returns monthly revenue by region. Then verify:

- Every table and column exists.
- The join keys are correct.
- The date filter is inclusive or exclusive as intended.
- The aggregation does not double count.
- The result row count and totals make sense.

Do not run generated SQL with production credentials.

### One-page recap

**ELI5:** the whole chapter in one breath.

- GenAI predicts plausible content; it does not guarantee truth.
- Strong prompts include role, context, task, constraints, format, examples, and a validation request.
- RAG retrieves context; fine-tuning changes behavior; agents use tools.
- Data engineers use GenAI for drafting SQL, code, schemas, tests, documentation, and pipeline skeletons.
- Synthetic data and anonymization need privacy and quality checks.
- Generated infrastructure and pipelines are drafts until reviewed and tested.
- NL2SQL needs the real schema, the right dialect, and result validation.
- Responsible AI requires fairness, transparency, privacy, security, accountability, and human oversight.
- The workflow is generate, inspect, test, validate, and sign off.

## Chapter 3 — Career and interview preparation

### What a data engineer actually does

**ELI5:** the data engineer builds the water system for the city — pipes, tanks, filters — so everyone else has clean water at the tap.

The core job is to build and maintain systems that collect, store, move, and clean data. You are the plumber and architect, not the person making the final dashboard or model.

Daily reality:

- Design and maintain batch and streaming pipelines.
- Model data in warehouses and lakes.
- Write SQL and Python.
- Fix broken jobs and slow queries.
- Ensure data quality, security, and cost efficiency.
- Work with analysts, scientists, and product teams.

Success looks like data arriving on time, complete, correct, and secure — and nobody notices, because it just works.

The role varies by company:

| Environment | Shape of the job |
| :--- | :--- |
| **Startup** | Broad generalist, lots of ownership |
| **Large enterprise** | Specialized teams, formal processes, scale |
| **Product company** | Pipelines tied to app events and experimentation |
| **Consulting** | Many clients, fast context switching |

### Paths in and opportunities

**ELI5:** many roads lead to the same city — pick the one you are already standing on.

| Background | Advantage | What to add |
| :--- | :--- | :--- |
| **Data analysis** | Strong SQL and business sense | Python, pipelines, cloud |
| **Software engineering** | Strong coding | SQL, data modeling, warehouses |
| **IT / DBA / sysadmin** | Infrastructure and databases | Python, ETL, cloud |
| **ETL / BI development** | Tooling knowledge | Python and cloud modernization |
| **Bootcamp or self-study** | Portfolio and projects | Real end-to-end work |
| **Another domain** | Domain knowledge | Technical fundamentals |

Job titles to search: Data Engineer, Analytics Engineer, Big Data Engineer, Cloud Data Engineer, ETL Developer, Data Platform Engineer, Data Architect, Database Developer, and DBA.

Industries: tech, finance, healthcare, retail, telecom, media, government, and consulting.

Titles are inconsistent. Read the responsibilities, not just the title.

### Skills employers want

**ELI5:** the job ad is a shopping list — make sure your basket has the items they actually check.

Must-have technical skills:

- **SQL** — joins, window functions, aggregation, performance.
- **Python** — pandas, APIs, file handling, scripting.
- **Data modeling** — normalization, star schemas, keys.
- **ETL/ELT** — pipelines and orchestration.
- **One cloud** — AWS, Azure, GCP, or IBM Cloud.
- **Databases** — relational plus at least one NoSQL or lake format.
- **Linux/shell basics** and **Git**.

Big data for larger companies: Spark, Hadoop concepts, and Kafka.

Nice to have: Docker, CI/CD, Terraform, dbt, and data quality tools.

Soft skills that get you hired: clear communication, debugging persistence, ownership, reliability, curiosity, and fast learning.

Show skills through projects with a README, clean code, tests, and a short write-up of decisions.

### Build a portfolio

**ELI5:** a portfolio is a fridge full of dishes you cooked — proof, not promises.

Include:

- Two to four solid projects, not ten shallow ones.
- An end-to-end pipeline: ingest, transform, store, query.
- At least one cloud project and one project with real messy data.
- A README per project: problem, architecture, tools, how to run, results.
- Clean code, tests, and a reproducible setup.

Project ideas:

- API → Python → database → dashboard.
- Web scraping, cleaning, and analysis.
- Batch ETL on a public dataset.
- Streaming demo with Kafka, even locally.
- A small warehouse with dbt models and tests.

What makes a portfolio stand out: an architecture diagram, evidence of tradeoff thinking, documentation a stranger can follow, and honest scope. Finished small projects beat abandoned big ones.

Avoid copied tutorial projects with no changes and notebooks with no explanation.

### Resume and cover letter

**ELI5:** a resume is a one-page advertisement — the recruiter spends seconds deciding whether to keep reading.

Resume rules:

- One page, two only if senior.
- Sections: Summary, Skills, Experience, Projects, Education, Certifications.
- Reverse chronological order.
- Consistent formatting, PDF export, ATS-friendly.
- No photo, age, marital status, or unnecessary personal details.

Bullet formula: **action verb + what you built + tool + measurable result**.

Weak: "Worked on data pipelines."

Strong: "Built an Airflow pipeline ingesting 2M daily events into Snowflake, cutting report latency from 6h to 30m."

Quantify volume, time saved, cost reduced, error rate, or users served. Tailor each application honestly. Group skills by category, not rating bars. Projects count as experience when you are starting out. Proofread.

Cover letter:

1. **Hook** — the role and why you are applying.
2. **Evidence** — one or two concrete achievements matching their needs.
3. **Fit** — why this company and team.
4. **Close** — enthusiasm and a call to action.

Keep it to half a page. Personalize it. Show, do not tell.

### References, pitch, research, and networking

**ELI5:** a referral is a warm introduction; a pitch is the 30-second version of your story.

References: ask first, brief them on the role, and keep the list current. Do not share someone's contact details without permission.

Elevator pitch structure:

```text
Who I am
  → what I do
  → a proof point
  → what I am looking for
```

Example:

> I am a data engineer focused on reliable analytics pipelines. I built an end-to-end ETL project that ingests API data, models it in PostgreSQL, and serves a dashboard. I am looking for a role where I can own pipelines and improve data quality.

Research the company, product, industry, data stack, recent news, and the interviewer's background. Use that research in your questions and your cover letter.

Network genuinely: former colleagues, meetups, online communities, alumni, and open-source contributors. Referrals beat cold applications. Ask for advice, not just a job.

### Assessing listings and applying

**ELI5:** read the label before buying — some "data engineer" jobs are really something else.

Read beyond the title:

- What are the day-to-day responsibilities?
- Which tools are actually used?
- Is it pipeline work, BI, DBA, or ML engineering in disguise?

Red flags: vague or contradictory requirements, "unicorn" lists, no mention of team or data scale, high turnover signals, and unpaid extensive take-home work.

Green flags: clear scope and stack, mentorship and growth, realistic requirements, and an engineering culture with tests, reviews, and documentation.

Apply with quality over quantity, apply early, use referrals, and keep a tracker of company, role, date, status, and contact. Follow up politely after a week.

### Technical review

**ELI5:** before the exam, review the basics — most interviews are won on fundamentals, not trivia.

SQL is the highest priority:

- Joins, aggregation, `GROUP BY` and `HAVING`.
- Subqueries and CTEs.
- Window functions: `ROW_NUMBER`, `RANK`, `LAG`, `LEAD`.
- `NULL` behavior and duplicates.
- Query performance: indexes and `EXPLAIN`.

Python:

- Data structures, loops, functions.
- pandas: load, clean, group, merge.
- File and API handling.
- Complexity basics.

Data modeling: normalization versus star schema, keys, constraints, and grain.

Pipelines: batch versus streaming, idempotency, retries, and orchestration.

Linux/shell: files, permissions, `grep`, `awk`, pipes, and cron.

Cloud basics: storage, compute, managed databases, and IAM.

Practice writing queries by hand, then run them. Explain your reasoning out loud.

### The interview process

**ELI5:** a fire drill before the fire — practice the moves so the real thing feels familiar.

Typical process:

1. Recruiter screen — fit, salary range, timeline.
2. Hiring manager screen — background, motivation, role fit.
3. Technical screen — SQL or Python, live or take-home.
4. Deep technical rounds — pipelines, modeling, system design.
5. Behavioral or values round.
6. Final or panel — cross-functional stakeholders.
7. Offer and negotiation.

Rehearse your elevator pitch, project stories in STAR format, SQL problems out loud, and behavioral answers about conflict, failure, ownership, and ambiguity. Do mock interviews. Prepare questions about the team, data stack, on-call, and success metrics.

Some questions are illegal or inappropriate: age, marital status, pregnancy, religion, disability, nationality, and sexual orientation. You do not have to answer. Redirect politely and know your local employment laws.

Salary expectations: research ranges and give a range, not a single number.

### Coding challenges and later rounds

**ELI5:** a small test kitchen — they want to see how you cook, not just what you claim.

Formats: live coding, take-home, pair programming, and whiteboard.

What they assess: problem-solving process, code quality, SQL fluency, and communication while thinking.

Live coding tips:

- Clarify the problem and edge cases first.
- Think aloud; silence is worse than imperfect reasoning.
- Start with a brute-force solution, then optimize.
- Test with small examples.
- Ask for hints if stuck.

Take-home tips:

- Read the rubric and deliver exactly what is asked.
- Keep it simple and tested.
- Document assumptions and how to run it.
- Submit on time; do not gold-plate.

SQL challenge pattern: join, filter, aggregate, rank, and explain the plan.

Second-round and final interviews dig deeper:

- Deeper SQL and Python.
- Data modeling and pipeline design.
- Debugging a broken scenario.
- System design: ingestion, storage, processing, serving, monitoring.
- Cross-functional collaboration.
- Behavioral ownership and prioritization.

How to stand out: structure answers as context, options, decision, tradeoff, and result. Admit unknowns and explain how you would find out. Connect technical choices to business impact.

Discussing a project: problem and constraints, architecture and tools, your specific contribution, challenges, results, and what you would change. Do not claim team work as solo work.

### After the interview and negotiation

**ELI5:** the game is not over at the final whistle — the follow-up and the deal matter too.

After the interview:

- Send a short thank-you within 24 hours and reference something specific.
- Reflect on what went well and what to improve.
- Follow up on the timeline if one was promised.
- Keep interviewing until you have a written offer.

Negotiation:

- Know your market range.
- Negotiate total compensation: base, bonus, equity, sign-on, benefits, and remote flexibility.
- Let them make the first number when possible; if pressed, give a researched range.
- Negotiate once, professionally.
- Get the offer in writing and review it.
- It is fine to ask for time to decide.
